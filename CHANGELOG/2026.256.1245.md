# 2026.256.1245 — ci(release): add workflow_dispatch so an existing tag can be published

## Summary

Add `workflow_dispatch` to `.github/workflows/release.yml` **gated to tag refs**, so an existing tag
created by `tag-on-merge` (which uses the REST API and emits no push event) can be published.

- `on: workflow_dispatch` is added;
- the job carries `if: github.event_name == 'push' || startsWith(github.ref, 'refs/tags/v')`, so this
  `contents: write` release workflow can **never** publish assets built from an arbitrary unmerged
  branch — a non-tag dispatch is skipped.

`tag-on-merge` created `v2026.256.1235` after the shared-host packaging bump (opencharly/sdk#258,
plugin PR #12) merged, but `on: push: tags` never fires for API-created tags, so that tag has no
release assets. The guarded dispatch (run with `--ref v<CalVer>`) is the explicit publish path,
mirroring charly's `release-binary.yml`.

## How tested

```
$ node -e "…YAML.parse('.github/workflows/release.yml')…"
parsed OK; job.if= github.event_name == 'push' || startsWith(github.ref, 'refs/tags/v')
```

After merge the workflow is dispatched for the existing tag:

```
$ gh workflow run release.yml -R opencharly/plugin-generate-packages --ref v2026.256.1235
```

which checks out the tag, builds `generate-packages-linux-{amd64,arm64}`, and attaches them (+ the
committed `.providers`) to the `v2026.256.1235` release. A dispatch on a branch is skipped by the
gate.
