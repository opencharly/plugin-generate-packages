# 2026.326.2154 — fix(pkg)!: adopt the current contract — the packages stop breaking pacman -Syu

## Summary

The packaging plugin was pinning a contract from 2026-10-06 — before opencharly/sdk#397 (2026-10-14) removed the variant family's mutual `Replaces`. Every package `charly-arch` built from it therefore still declared `charly`, `charly-full` and `charly-minimal` as each replacing the other two, so a routine `pacman -Syu` resolved two of them and refused:

```
:: charly-full-2026.326.1922-1 and charly-minimal-2026.326.1922-1 are in conflict
error: unresolvable package conflicts detected
error: failed to prepare transaction (conflicting dependencies)
```

This is the residual cause of **opencharly/layer-charly#23**: republishing the charly release was not enough, because the *packaging plugin* is the stale producer. Measured on the republished `2026.326.1922` packages, their control metadata still carries `Replaces: charly-full charly-minimal`.

- **sdk `v0.2026279.2204` → `v0.2026326.2119`, spec `v0.2026276.0` → `v0.2026326.2005`** — the current contract modules, which carry `packagekit`'s no-`Replaces` rule.
- **The E2E test asserted the broken behaviour.** `TestGeneratePackagesE2E` required `replaces = charly` in the minimal `.PKGINFO`. It now asserts what the contract defines: `provides` and `conflict` on the family, and **no** `replaces` — so a regression to a mutual replace fails here rather than in a user's `pacman -Syu`.
- Two lint findings are fixed that this repo's CI never saw: an unchecked `fmt.Fprintln` in `plugin.go`, and `cue.Value.Struct()` (SA1019) in `schema_splice_test.go`. Both **pre-exist on `main`** — the file and line are identical there, and `cuelang.org/go v0.16.1` is unchanged by the pin bump (an earlier draft of this body wrongly blamed a newer cuelang; the diff itself disproves it). This repo ships no `.golangci.yml` and runs no `golangci-lint` in its workflows, so nothing had flagged them until I ran the gate locally for this change.
