# 2026.327.0054 — feat(cli)!: --release, so a packaging repair is published as a new pkgrel

## Summary

Exposes the one case that needs a package release: **republishing an already-shipped version whose packaging changed**. That is exactly `opencharly/layer-charly#23` — the charly packages at `2026.326.1922` carry the variant family's mutual `Replaces` and must be republished as `-2`, because a client that already holds `-1` would never see a rewritten `-1`.

- **`--release <n>`** passes straight into `packagekit.BuildOptions.Release` (`opencharly/sdk#618/#620`). Empty keeps nFPM's normal naming — so a normal release changes nothing at all, which `opencharly/sdk#620` guarantees and the existing E2E asserts.
- **A new end-to-end test** pins the repair case: `--release 2` produces `charly-<ver>-2-x86_64.pkg.tar.zst` and its `.PKGINFO` carries `pkgver = <ver>-2`.

Two pins move: `github.com/opencharly/sdk v0.2026326.2119 → v0.2026326.2300` (the release that carries the corrected `Release` default and the field), and `github.com/opencharly/spec v0.2026326.2005 → v0.2026326.2226`, which the sdk release itself requires — the same bump every module in this chain takes when it adopts that sdk.
